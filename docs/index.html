Which page should an editor refresh first? An honest, audited priority score

Author: Amrit  ·  Lane: Refresh / Content Opportunity Scoring  ·  Date: September 2026
Repo & notebooks: github.com/yashkrverma1234-glitch/ml-internship-assignment1

0.Abstract

Question. Which of a client's content pages should an editor refresh first, this month?

Data. 30,000 pseudonymized pages across 32 clients, combining Google-Search-Console-style performance, on-page signals, and behavioral analytics — no client names, URLs, or raw queries.

Method. A transparent rule baseline (CTR gap vs. position-tier median, weighted by traffic and staleness) compared against a Logistic Regression trained on an observed decline label, validated with a client-grouped holdout so the model is judged only on clients it has never seen.

Headline result. The full-feature model edges the baseline (precision@50 = 0.74 vs. 0.72). Attacking our own model found that three features numerically overlap the label's own time window. Removing them — the honest, shippable model — drops precision@50 to 0.46 against a base rate of 0.542. That disclosed number, not the flattering one, is what we ship.

What it's for. A ranked, capped, human-reviewed action queue for editors — not an autonomous refresh trigger.

1.Problem framing

Decision: which pages an editor should refresh first, out of thousands, given limited time. Unit of analysis: one page for one client, one snapshot in time. Output: a 0–100 priority score plus a recommended action (refresh_priority / refresh_review / monitor / insufficient_data).

Who acts on it: a content/SEO editor or team lead, working a client's page list weekly.

Cost of a wrong call: a false refresh_priority wastes editor hours on a page that would have recovered anyway; a missed decline lets organic traffic keep eroding, silently, for another month.

Why ML, not just a rule: the rule baseline already captures the obvious signal (CTR below what similarly-ranked pages get). A learned model earns its place only if it beats that rule on the same audited split and metric — which is exactly what Sections 4–5 test, including the case where it doesn't hold up.

2.Data safety

Modeling uses only the local, pre-anonymized starter file (30,000 rows, 32 pseudonymized client IDs) — not the gated internal warehouse. Deliberately excluded from features:

  • trend_direction, trend_pct — these define the label; including them would mean the model learns the label from itself.
  • content_id, client_id — identifiers, used only for grouping the train/test split, never as model inputs.

Client and content IDs throughout this repo and page are pseudonymous placeholders from the anonymized dataset — no client names, URLs, or raw search queries appear anywhere in work/ or on this page.

3.Baseline

A transparent rule, baseline_action_score: for pages with enough traffic to trust (impressions_90d ≥ 500) and a known ranking position, score = (tier-median CTR − page CTR, floored at 0) × log(1 + impressions_90d) × a 1.15× bonus if the page hasn't been touched in 180+ days. It uses no label-derived fields, so it's a fair, non-circular target for the model to beat — on the same split, same metric.

4.Model / analysis

Method: Logistic Regression, compared against a Random Forest (Random Forest did not win — see Section 5). Target: is_declining_label = (trend_direction == "down"), an outcome observed in the data, not a rule we defined. Features: search performance (ctr, avg_position), on-page (word_count, content_age_days, days_since_last_update), behavioral (engagement_rate, scroll_rate, ai_traffic_pct), and categorical tiers (content_type, main_intent, position_tier, freshness_tier, …). Left out on purpose: impressions_90d, clicks_90d, sessions_90d — see Section 5, this is the paper's central finding, not an oversight.

5.Evaluation

Split: client-grouped 80/20 (27,675 train / 2,325 test rows, 6 of 32 clients held out entirely) — never a random row split, because rows from the same client share hidden character a random split would let the model memorize.

Control check: re-running the same model on a naive random split kept ROC-AUC almost flat (0.698 vs. 0.725 grouped) but inflated precision@20/50/100 to 0.95 / 0.90 / 0.87 — proof the naive split was letting the model memorize clients, concentrated exactly where the product looks: the top of the ranked queue.

The error we went looking for: impressions_90d, clicks_90d, and sessions_90d numerically overlap impressions_last_30d / impressions_prev_30d — the exact 30-day sub-windows the label's own source column, trend_pct, is computed from. Dropping them moved ROC-AUC only slightly (0.725 → 0.707) but collapsed precision@20 from 0.80 to 0.25 and precision@50 from 0.74 to 0.46 — a 38% drop concentrated entirely at the top of the ranking, the part the product actually surfaces to editors.

6.Interpretation

The full-feature model's apparent win over the baseline (0.74 vs. 0.72) was mostly an artifact of window overlap, not real signal the model discovered. Once that's removed, the honest picture is: a simple CTR-gap rule and a leakage-clean model perform in the same neighborhood, with the model still adding value in ranking quality (ROC-AUC 0.71 vs. the baseline's 0.54) even though its precision@50 is lower than the baseline's headline number. That's a legitimate, if unglamorous, finding: the obvious rule was already pretty good, and the model's real contribution is a more principled ranking, not a dramatically higher hit rate.

7.Recommendation

Production scoring blends the leakage-clean model with the baseline (0.65 × model probability + 0.35 × normalized baseline score), refit on all 32 clients, then routed through a no-go filter for pages we don't have enough signal to score responsibly.

Only 5.5% of pages get flagged as top priority; 23.6% are held back as insufficient-data rather than force-scored.

  1. Ship as decision support, not automation. Route refresh_priority pages to editors as a ranked queue; never auto-trigger a refresh.
  2. Quote precision@50 = 0.46 (base rate 0.542) to stakeholders — the honest, held-out, leakage-clean number, not 0.74.
  3. Review the concentrated clients first. 84.1% of refresh_priority flags land on just 5 of 32 clients — validate the model isn't overfitting to a couple of clients' quirks before wider rollout.
  4. Treat the 23.6% marked insufficient_data as a data problem, not a scoring failure — give them time to accumulate signal.
  5. Don't claim causal impact yet. Nothing here supports "refreshing causes recovery" without a controlled experiment (e.g., randomizing refresh order within the refresh_review tier).

Limitations

  • The baseline rule also uses impressions_90d as a volume floor and multiplier — the same column implicated in the overlapping-window leak. Its 0.72 precision@50 should be read as an upper bound, not a re-audited clean number.
  • Every page is one snapshot in time, not tracked longitudinally — we can't fully separate "this page is declining" from "pages like this, right now, tend to look this way."
  • A page's refresh history reflects an editor's past choice, not a random assignment, so any refreshed-vs-not comparison is associational, never causal.
  • 26.6% of pages have fewer than 100 impressions/90 days; their scores carry deliberately low confidence.
